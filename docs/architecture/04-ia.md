# 04. Architecture de l'IA

L'IA est un **service interne externe au Compose** (K4). Odin l'utilise pour : **comprendre** les rapports (extraction), **répondre** (assistant), **produire** (synthèses, plus tard rapports et présentations). Ce fichier fixe **comment** Odin s'y relie, pour que les **règles IA du fichier 06 des spécifications** (IA-01 à IA-22) soient **garanties par construction**.

> **À confirmer d'urgence** : les capacités réelles du service IA (voir `09-questions-ouvertes-et-prototypes.md` Q-A1). Tout ce qui suit est conçu pour **fonctionner avec un service de modèle de langue exposant une API de type « conversation » standard**, et **se dégrader proprement** si certaines capacités manquent (sortie structurée contrainte, embeddings, grand contexte).

## 1. Port `ai-gateway` (adaptateur remplaçable)

Le noyau d'Odin ne connaît **qu'une interface** :

| Capacité du port | Usage | Remarque |
|---|---|---|
| `extractStructured(texte, schéma, instructions)` | Extraction de faits, classification, détection | Renvoie un **objet conforme à un schéma strict** ou une erreur |
| `answer(contexte autorisé, question, règles)` | Assistant (lot 1) | Renvoie texte + **références d'extraits** |
| `summarize(contexte autorisé, consigne)` | Synthèses (lot 1 : résumé de fiche ; lot 5 : rapports) | Même contrainte de références |
| `embed(textes)` | Recherche sémantique | **Optionnel** : voir §6 |
| `health()` | Disponibilité, latence, version | Alimente le mode dégradé |

**Adaptateurs** : (1) service **compatible avec l'API de conversation standard** (le plus probable) ; (2) service **spécifique** de l'organisme / de l'État si l'API diffère ; (3) **simulateur** pour les tests (réponses rejouées).

**Rien d'autre** n'est exposé au métier : pas d'invites dans les modules métier, pas de noms de modèles dans le code métier.

## 2. Principe de sécurité central : le modèle n'agit pas

Conformément à X5 et IA-12 :

1. Le modèle de langue **ne dispose d'aucun outil** à effet de bord (pas d'écriture, pas d'appel réseau, pas d'envoi) ; il **renvoie du texte ou un objet structuré**.
2. **Du code déterministe** reçoit, **valide** (schéma, preuves, droits, seuils) et **écrit**. Aucune instruction contenue dans un document ne peut donc **déclencher** une action : au pire, elle **fausse une proposition**, qui est ensuite **rejetée par validation** ou **revue par un humain**.
3. Les propositions sont **toujours** au niveau F0 ; **aucune** action de validation ne passe par l'IA.
4. Les **documents** sont insérés dans les invites comme **données délimitées**, jamais comme instructions du système ; les invites d'extraction **interdisent** d'obéir au contenu.
5. Un **détecteur d'injection** (règles + classification par le modèle) signale les documents suspects (MSG-32) mais **ne remplace pas** les points 1 à 4.

## 3. Pipeline d'analyse d'un rapport (module `analysis`)

Machine à états **persistée en base** (reprise après panne, idempotence), exécutée par les workers :

| Étape | Entrée | Traitement | Sortie | Si échec |
|---|---|---|---|---|
| 1. **Contrôle** | Fichier | Empreinte, type, taille, antivirus, doublon exact | OK / refus motivé | Message MSG-60/61 |
| 2. **Extraction de texte** | Fichier | **Service `extractor` isolé** : texte, tableaux, métadonnées | Texte normalisé + structure | Rapport conservé ; saisie manuelle possible |
| 3. **Détections déterministes** | Texte | Données personnelles (motifs, listes), marquages de classification, consignes suspectes | Drapeaux | Étape non bloquante |
| 4. **Découpage** | Texte | Découpage en extraits adressables (positions) | `chunks` | — |
| 5. **Classification** | Texte (extrait) | Type de rapport, période, niveau suggéré (règles + modèle) | Propositions | Valeurs par défaut du gabarit |
| 6. **Extraction de faits** | Extraits + schémas des natures | Modèle de langue, **sortie à schéma strict** | Faits candidats avec extrait cité | Reprise ; si répété → signaler |
| 7. **Vérification des preuves** | Faits candidats | **Chaque extrait cité doit exister mot à mot dans le texte source** ; sinon le fait est **rejeté** | Faits prouvés | Compte-rendu des rejets |
| 8. **Rattachement** | Faits prouvés | **Candidats fermés** : alias exacts + trigrammes + vecteurs ; le modèle **choisit** parmi les candidats, **ne génère pas** d'identifiant | Objets rattachés (certain / ambigu) | File de curation |
| 9. **Politiques de contenu** | Faits | Retrait des passages évaluatifs nominatifs ; pas de faits sur personnes (IA-08) ; masquage de données personnelles | Faits filtrés + avertissements | — |
| 10. **Confiance** | Faits | Score composite (voir §4) | Confiance haute / moyenne / faible | — |
| 11. **Contradictions** | Faits + existant | Règles du fichier 02 du lot 1 §5 (déterministes) | Signaux, précisions | — |
| 12. **Persistance** | Résultats | Faits F0, preuves, signaux, avertissements ; événement | `ReportAnalysisCompleted` | — |

**Documents longs** : découpage en parties, extraction **par partie**, puis **fusion et déduplication** des faits (clé : nature + objet + étiquette + valeur).

**Idempotence et reprise** : chaque étape est **rejouable** ; une panne du service IA met l'analyse en **attente** avec attente croissante, **sans perte**.

## 4. Confiance : composite, jamais « déclarée » par le modèle

Le niveau de confiance (haute / moyenne / faible) est calculé par du code à partir de **signaux observables** :

- Exactitude de l'**extrait** (présent mot à mot) : condition **nécessaire**.
- **Validité du schéma** et complétude des champs obligatoires.
- **Rattachement** : alias exact (fort), un seul candidat (moyen), plusieurs (ambigu).
- **Cohérence entre deux passes** (même extraction répétée avec une variation) : accord = bonus.
- **Cohérence avec l'existant** (valeur proche du fait précédent).
- **Signaux de risque** : contexte manquant, valeur inhabituelle (baisse d'avancement), détection d'injection.

Les **seuils** (PAR-01..03) sont **calibrés** sur le jeu de référence (fichier 05 du lot 1 + corpus réel anonymisé). **Aucun** score n'est présenté à l'utilisateur comme une probabilité ; seulement un **niveau**.

## 5. Assistant : récupération filtrée par droits (RAG sûr)

1. **Principal** construit depuis la session (rôles, périmètres, habilitations).
2. **Recherche hybride** (texte + sémantique) **avec le filtre de droits dans la même requête SQL** : les extraits non autorisés **ne sont jamais lus** par le processus qui parle au modèle.
3. **Invite** = règles fixes + extraits autorisés (avec identifiants) + question. **Pas de contenu hors droits dans l'invite**, donc **aucune fuite possible par le modèle**.
4. **Réponse** : le modèle doit **citer des identifiants d'extraits** ; le code **vérifie** que chaque identifiant cité fait partie de l'ensemble autorisé **et** que l'affirmation y est effectivement supportée (contrôle de recouvrement lexical) ; sinon l'affirmation est **retirée** ou la réponse **refusée**.
5. **Chiffres** : uniquement ceux **fournis comme données** (indicateurs, faits) : le modèle ne génère pas de chiffre libre (IA-04). Le code **recompose** les chiffres à partir des données, le modèle ne fait que **rédiger autour**.
6. **Refus** : requêtes d'évaluation de personnes, de contournement, d'exécution d'instructions de documents : détectées **avant** l'appel (règles + classification) et **après** (contrôle de sortie).
7. **Journalisation** : métadonnées d'usage seulement (qui, quand, périmètre, version du modèle et des invites) ; **le texte des questions n'est pas journalisé côté administration** (RG-22).
8. **Mode dégradé** : si le service IA est indisponible, repli sur la **recherche textuelle** simple (EX-ASS, T-ASS-09).

## 6. Embeddings (recherche sémantique)

Deux options, à trancher selon la réponse du service IA (Q-A1) :

| Option | Quand | Avantages | Inconvénients |
|---|---|---|---|
| **A. Le service IA fournit les embeddings** | Il expose un modèle d'embeddings | Aucun composant de plus ; cohérent | Dépendance de disponibilité ; chaque indexation passe par le service |
| **B. Petit modèle d'embeddings local dans le Compose** (CPU suffisant) | Pas d'embeddings fournis, ou volonté d'indépendance | Indépendance, coût nul, fonctionne en mode dégradé | Un conteneur de plus ; mise à jour du modèle à gérer |
| **C. Pas de sémantique au lot 1** | Besoin de livrer vite | Plus simple | Rappel moindre de l'assistant ; **la recherche textuelle reste complète** |

**Recommandation provisoire** : **B** si l'option A n'est pas disponible, sinon **A** ; **C** accepté pour un premier incrément. Le port `embed` isole le choix.

## 7. Politique par niveau de classification (à décider)

Le service IA interne est-il **habilité** à traiter les contenus de niveau N4 (sécurité) ou de défense ? Ce n'est pas une question technique : elle relève de l'organisme. Odin implémente une **règle paramétrable** : « niveau maximal autorisé à être envoyé au service IA » (par défaut **N3**). Les contenus au-delà sont traités **sans IA** (saisie manuelle, détections déterministes) et **marqués** en conséquence. Voir Q-A2.

## 8. Qualité et évaluation continue (IA-20)

- **Jeu de référence** (corpus fictif + corpus réel anonymisé, annoté) versionné dans le dépôt.
- **Harnais d'évaluation automatisé** : exécute le pipeline sur le jeu, calcule **rappel et précision par nature de fait**, **taux de faits évaluatifs** (doit être 0), **taux d'injection exécutée** (doit être 0), **taux d'extraits non vérifiables** (doit être 0).
- **Porte de qualité** : un changement d'invite, de modèle ou de seuil **ne peut être déployé** que si les mesures du jeu de référence respectent les seuils (voir fichier 04 du lot 1 §IAX).
- **Registre des versions** : invites, schémas, modèles, **toujours journalisés** avec chaque analyse (RG-22, EX-AUD-05).
- **Retour utilisateur** (rejets, corrections) → **tableau de bord** de qualité (L1-I11) → alimentation du **jeu de référence** (avec accord).
- **Retour arrière** : la configuration IA (invites, seuils, modèle) est **versionnée** et **restaurable** immédiatement.

## 9. Gestion de la charge et résilience

- **Concurrence bornée** : le nombre d'appels simultanés au service IA est **paramétré** (le débit est limité par le service, pas par Odin).
- **Priorités** : interactif (assistant) > analyses de rapports > recalculs en masse.
- **Délais d'attente et reprise** : délais et tentatives paramétrés ; **disjoncteur** (circuit breaker) : après N échecs, Odin **arrête d'appeler** le service, passe en mode dégradé, **teste périodiquement** et **reprend seul**.
- **Débit et coût** : les appels sont **mesurés** (jetons, durée) par analyse ; un plafond quotidien paramétrable évite l'emballement.
- **Isolation des pannes** : l'indisponibilité de l'IA **n'affecte pas** les parcours sans IA (X6).

## 10. Ce que l'IA ne reçoit jamais

- Contenus au-dessus du niveau maximal autorisé (§7).
- Contenus hors des droits de l'utilisateur demandeur (assistant).
- Identifiants techniques, secrets, journaux, données d'authentification.
- Textes d'alerte protégée détectés (RG-24).
